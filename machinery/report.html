What these numbers establish

  • Timing boundary. Execution brackets repeated run(state) calls inside the child. Preparation, warmup, stdout, controller checks and shutdown are outside it. Whole-process time includes those lifecycle stages. Empty cases expose a floor; nothing is subtracted.
  • GC evidence. Every BAML and Go allocation trial must observe at least three natural collections during execution. Shutdown-only GC does not qualify. Python reports cyclic collections only; Rust has no tracing collector; Node/Bun GC coverage is unknown.
  • Memory interpretation. Peak RSS is a process high-water mark, not retained heap. Higher retention also increases checksum traversal. This experiment does not isolate collector copying or pause cost.
  • Telemetry validity. Local BAML recordings are checked after the trial for decodability, references, root completions and expected run() counts. High also requires run spans. The pinned release does not emit RecordingEnd or names; IDs are joined from the measured engine.
  • Instrumented host. BAML runtime trials use a source-built release probe. A metadata snapshot taken after execution supports recording checks and remains in whole-process CPU/RSS. Published packed-executable observations are separate; they are not the runtime-trial distribution.
  • Statistical limits. Twenty fresh-process trials per configuration, in randomized order, with fixed warmup and work counts. Min–max shows the observed range, not uncertainty bounds. These finite batches do not prove JIT convergence, per-call tail latency or persistent-service behavior.
  • Unmeasured. HTTP load, cloud telemetry, LLM capture, incremental compilation, non-BAML complete deployment inventories and BAML pause attribution are outside this collection. Source-level calls may be optimized away.
