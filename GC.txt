How GC changes the comparison

The inspected BAML source has a generational copying collector. The engine requests
exclusive heap access, waits for holders to park, scans roots, collects, repairs
references, releases permits, then runs post-GC work. Generated Rust still needs
this roots/safepoints/mutation contract if it retains BAML's heap semantics.
Replacing the dispatch loop alone does not remove allocation, copying or telemetry.

Go 1.26.3 runtime/mgc.go describes concurrent mark/sweep with write barriers and
allocation assists, plus stop-the-world sweep/mark termination. Concurrent does
not mean pause-free or free CPU. Rust here uses ownership/Rc: destruction and
allocator work still cost CPU. Python refcounting/cyclic GC and V8's collector/JIT
are separate policies. Equal object counts do not imply equal bytes or work.

Use normal GC policies for headline runs. Sweep allocation batches with a fixed
retained ring, then ring capacity at fixed churn. Run long enough to observe several
natural collections. No result currently proves this happened: the portable runner
records OS resources, not collector events. Short validation runs are insufficient.

For causal attribution, build the SAME BAML revision with bex_engine/gc_profiling
and collect its bex_gc debug events through a configured tracing subscriber.
Feature and subscriber are both required; setting an environment variable alone
does not create missing instrumentation. The existing gc_profile.rs defines:
  park_wait: request -> exclusive access; not a uniform application-wide pause.
  pause: exclusive-access interval, containing root scan, heap work and fixup.
  post_gc: callbacks/finalizers after permits are released.
  total: whole cycle. Do not add pause to its constituent phases again.
  new_objects: actual TLAB allocations; NOT bytes or backing-store allocations.
  generation/capacity slots: storage counts; NOT live reachable bytes.
Record minor/major reason, counts, pause distribution/max, roots, retained objects,
and payload allocations. Check the implementation for the measured revision.

Use a separate Go diagnostic run with runtime/metrics or gctrace to capture GC CPU,
assists, live heap and STW pauses. Keep diagnostic runtime flags/builds explicit.
Correlate collector events with scheduled-arrival HTTP latency on a common timeline;
slow requests alone do not identify GC. Include waiting for safepoints and allocator,
scheduler, validation and telemetry costs in alternative explanations.

Then repeat performance with production-equivalent instrumentation. Forced GC is
only a correctness/stress experiment; correctness.baml uses it to test live roots.
Do not tune one runtime's heap without recording the policy and memory tradeoff.
An RSS plateau does not prove no leak; a rising RSS does not prove one either.
